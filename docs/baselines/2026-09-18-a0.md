## 3. 如何复跑

从项目根目录执行，使用独立 PowerShell 子进程，不需要启动 Flask、Docker 或激活虚拟环境：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/check_baseline.ps1
```

也可通过 `-PythonPath` 指定另一个已装好依赖的 Python。脚本不安装包，不调用真实部署，不修改系统执行策略；`Bypass` 仅作用于此次 PowerShell 进程。脚本会列出已装包、运行依赖检查/单测/插件语法检查；任何检查失败都使脚本失败。

隔离原因：`tests/test_llm_api.py` 导入 `app`，导入时就会初始化数据库。脚本在导入前覆盖全部当前后端配置键，使用内存数据库、假 API key 和本机不可用的模型地址，结束后还原进程环境。当前测试中的外部调用还依赖 Mock；这不是通用网络沙箱，未来新增测试也必须审查副作用。

等价核心测试命令是：

```powershell
# 仅在专用测试终端中设置；运行真实后端前关闭该终端。
$env:DATABASE_URL = 'sqlite:///:memory:'
$env:OPENAI_API_KEY = 'baseline-not-a-real-key'
$env:OPENAI_BASE_URL = 'http://127.0.0.1:9/v1'
$env:OPENAI_MODEL = 'baseline-model'
$env:OPENAI_TIMEOUT = '1'
$env:TASK_WORKSPACE_ROOT = Join-Path (Get-Location) 'runtime/a0-baseline/workspaces'
.\venv\Scripts\python.exe -m unittest discover -s tests -v
```

新环境应分别记录代码 commit、依赖版本、操作系统、失败用例和命令退出码；不要通过删测试、放宽断言或临时跳过来维持“40 个通过”。首次干净安装与 Linux 测试属于后续交付验证。

## 4. 当前 API 清单

依据 `backend/__init__.py` 和 `backend/routes/`，共 7 个业务路径，不计 Flask 自动生成的静态文件、HEAD/OPTIONS 路由。

| 方法与路径 | 当前行为 | 改造边界 |
| --- | --- | --- |
| `GET /health` | 后端进程健康响应 | 复用简单入口；将来单独增加依赖就绪检查 |
| `POST /api/llm/intent` | 单次模型调用，返回意图与模型生成的置信度 | 保留 legacy；不是多轮诊断或经过校准的授权信号 |
| `POST /api/llm/dispatch` | 按意图与客户端 context 返回流程建议 | 保留 legacy；客户端传来的测试通过标志不是可信审批 |
| `POST /api/tasks/prepare` | 校验请求，在后端主机 clone 到 workspace | 本地受信任用户使用；未来远程 Agent 不注册此入口 |
| `POST /api/tasks/execute` | 同步拉取、安装、测试、门禁、部署/监测，结束后写历史 | 本地 legacy；不直接作为远程任务或模型工具 |
| `GET /api/tasks/history` | 返回最多 100 条摘要，默认 20 条 | 保留旧历史；新 Agent 事件与证据另建模型和授权接口 |
| `GET /api/tasks/history/<int:record_id>` | 返回单条详情，不存在则 404 | 保留旧历史；目前没有记录级权限控制 |

当前 `create_app()` 无条件注册旧路由，`app.py` 使用本机绑定的 Flask debug 服务。**目前尚无“云端关闭 legacy 路由”的实现**，配置草案也不会产生这个效果。不得直接改成公网监听并视为完成远程交付。

## 5. 数据库、执行器与插件盘点

### 数据库存储

唯一业务表为 `task_execution_records`（`backend/models/task_record.py`）：

- 标识与摘要：`id`、`intent`、`repo_url`、`project_type`、`status`、`message`、`created_at`。
- JSON 文本：`repository_json`、`task_request_json`、`install_result_json`、`test_result_json`、`deploy_result_json`、`dispatch_result_json`。
- 监测结果嵌在部署 JSON 内；阶段耗时和状态摘要由结果字段提取，并非独立事件流。

`backend/db.py` 用 SQLAlchemy `create_all` 初始化表，没有 Alembic 迁移。`task_history_service.py` 提供写入、列表、详情，`routes/tasks.py` 在流程结束后写入；没有执行前持久化任务、租约、审批或中断恢复。此次未打开真实历史库。

复用 SQLAlchemy 和旧历史查看能力；新 PostgreSQL 表及迁移在 A1/A3 逐步建立，不把旧 JSON 记录当作已验证发布或恢复授权，不直接破坏已有 SQLite 数据。

### runner 与 deployer

| 模块 | 当前行为 | 后续处置 |
| --- | --- | --- |
| `repo_fetcher.py` | Git 浅克隆，由请求指定分支/commit，在后端主机执行 | 保留本地；Agent 首版接入已登记发布，不执行陌生仓库 |
| `test_runner_factory.py` + `test_runners/` | 按用户填写的 python/nodejs/java 选择 runner，执行命令 | 保留本地回归；不是自动识别仓库，也不是隔离执行平台 |
| `task_dispatcher.py` | deploy/package/merge 按测试通过布尔值设门禁 | 复用门禁思路，不复用为恢复审批机制；流程建议不代表打包/合并已实现 |
| `DockerDeployer` | Docker CLI build/run，inspect 容器状态 | 保留 legacy，不作为 Kubernetes 恢复工具 |
| `ServerDeployer` | 在后端所在主机执行脚本/启动命令，可选 HTTP 检查 | 不是 SSH 远程主机管理，不授予 Agent 任意 shell |
| `AzureDeployer` | 后端主机调用 Azure CLI 模板部署或自定义命令，可选 HTTP 检查 | 代码存在、Mock 通过；本次未验证真实 Azure 部署 |

部署器及 runner 都在后端主机上下文工作；Docker/Azure CLI 的实际目标还取决于外部 CLI 配置，并不是经过本项目登记、校验的集群身份。
