# ADR-0001：增量改造、先只读调查、受限恢复

日期：2026-09-18。状态：**已采纳的设计决策，运行时约束待实现**。

依据：[主技术方案](../tech_design.md)、[A0 实测与盘点](../baselines/2026-09-18-a0.md)。修改本决策范围必须新增 ADR，说明动机、权限影响和新增验收，不把范围扩展藏进一个工具参数中。

## 背景

现有系统能按结构化请求运行本地 CI/CD 流程，但执行依赖后端主机、同步子进程和最后写入的 JSON 历史。它没有可靠异步任务、集群身份、证据关联、审批或恢复验证，不能将旧接口接上模型就称为可落地的运维 Agent。

现有 Flask、SQLAlchemy、插件和失败联调经验值得保留。工程重点转为可核查的诊断、权限边界和可验证恢复，而不是重写框架或无限增加部署器。

## 决策一：冻结第一版范围

| 维度 | 第一版范围 |
| --- | --- |
| 使用对象 | 一个受邀团队；管理员登记一个集群，不接受请求临时提供 kubeconfig 或任意 API 地址 |
| 集群 | ECS 自建 K3s 实验环境；指定 namespace；不宣称 ACK 接入或控制面高可用 |
| 应用 | 登记的无状态 HTTP Deployment + Service；登记包含资源身份、发布及验证规则 |
| 首批故障 | 镜像拉取失败、启动崩溃、Readiness 失败；证据不足就移交人工 |
| 第一版唯一写动作 | `restore_verified_pod_template`：恢复登记 Deployment 中已验证健康的 Pod template |
| 允许写入的前提 | 有可信发布快照、digest、仍匹配的依赖配置、有效人工审批，目标 UID/配置未漂移 |
| 成功条件 | 实际目标版本、资源归属、就绪状态及业务断言共同通过；HTTP 200 或命令退出 0 单独不够 |

批准绑定精确计划哈希、目标 UID、配置哈希、目标快照、差异、验证规则和有效期；改计划或目标发生变化必须重新评估/审批。模型建议不能充当审批，客户端布尔值不能充当可信发布记录。

恢复动作不修改 Service、ConfigMap、Secret、数据库或外部状态。原地配置变化、无可信健康基线、GitOps 管理或存在数据迁移时只读诊断/移交人工。首版不做任意 patch、SSH、节点重启、RBAC 修改、删除 PVC/namespace、购买云资源或无人审批的生产发布。

这些是后续验收约束。A0 没有安装集群、实现审批或开放任何写操作。

## 决策二：保留框架，分开旧执行链路和新 Agent

复用 Flask 的应用组织、SQLAlchemy 的 ORM 能力、插件入口和状态/耗时展示经验。新增独立的 `/api/v2` 入口、新业务模型及迁移；不把 `execute_task_pipeline` 逐渐改成万能 Agent。

旧 runner/deployer、同步接口和 SQLite 历史保留在本地 legacy 模式。新云端入口必须按明确模式只注册新路由，并用路由测试证明不能调用任意执行接口；**当前应用尚未具备模式隔离能力**。新 Agent 代码不得导入旧 `run_shell_command`/`run_command` 作为工具执行捷径。

数据库演进使用显式迁移，旧历史先保留，不直接改写为 Incident/Release 或凭据。独立模型和进程身份的改造逐步落实，不通过移动文件目录假装完成隔离。

取舍：保留两条链路会增加一段时间的维护成本，但避免丢失原有成果，也更容易用已有测试区分回归。暂不切 FastAPI、拆微服务或同时引入多个 Agent 框架；遇到可测量的瓶颈再做针对性决策。

## 决策三：先实现只读调查，再开放恢复

顺序为 A1 证据登记/关联 -> A2 有界诊断 -> A3 持久化、身份和任务可靠性 -> A4 审批恢复 -> A5 独立验证。A1/A2 可先使用固定样本开发，但真实能力声明必须有集群契约测试。

`DiagnosticEngine` 适配固定版本的 HolmesGPT，工具循环只接受受控证据接口。模型进程不持有集群凭证；网关只读指定对象/namespace、脱敏限长，保留证据身份与来源。日志和仓库文本是不可信数据，不是扩大权限的指令。

取舍：首批用户不能让 Agent 自动写集群，但可以先验证取证与诊断是否有效，同时缩小错误模型输出的影响面。不自研第二套通用 Agent 框架，把自主工程重点放在证据、任务、策略、审批与验证上。

## 决策四：恢复不是模型生成的 shell

恢复执行器使用独立系统身份、受限写凭证和结构化 Kubernetes API。它只读取已持久化且有效的审批动作，执行确定性的前置条件与字段检查；模型无法直接调用它，也不能提供任意 kubectl、shell 或 patch 内容。

同一目标串行操作；执行结果未知时进入核对流程，不因 Worker 超时或租约过期直接重发。验证器独立判定是否恢复，模型的置信度不能把失败改为成功。数据库不可用时不绕过持久化执行写动作。

取舍：动作覆盖面很窄，无法自动处理所有故障；换来明确的权限、幂等和测试边界。增加第二种动作前，必须补审批语义、失败补偿、验证规则和回归集，而不是增加一个命令输入框。

## 模块位置与依赖方向

下列为**规划位置**，按对应阶段创建真实实现；A0 不生成空类或占位接口来冒充已完成。

| 位置 | 责任 | 首次实施 |
| --- | --- | --- |
| `backend/registry/` | Cluster/Application/Release 登记、范围解析与发布快照 | A1 |
| `backend/tools/` | 结构化只读 Kubernetes 适配、证据网关；唯一读取集群凭证的诊断侧模块 | A1 |
| `backend/evidence/` | Evidence 元数据、脱敏、规范化哈希与内容存储引用 | A1 |
| `backend/models/`、`backend/schemas/` | 新模型与输入契约；与 legacy 请求分开 | A1/A3 |
| `backend/diagnostics/` | `DiagnosticEngine` 接口、HolmesGPT 适配、预算与报告引用校验 | A2 |
| `backend/incidents/` | 调查领域状态、事件与流程编排，不直接运行 shell | A2/A3 |
| `backend/routes/incidents.py`、`backend/routes/releases.py` | 新增 v2 路由，不能绕过身份、登记和策略校验 | A1/A3 |
| `backend/jobs/`、`migrations/` | PostgreSQL job、租约、幂等、中断核对；Alembic 迁移 | A3 |
| `backend/security/` | 身份认证、应用级授权、审计上下文 | A3；远程开放前必须完成 |
| `backend/policies/` | 字段白名单、计划哈希、审批有效性与目标漂移检查 | A4 |
| `backend/executors/` | 独立进程入口、恢复动作与执行结果核对，不提供通用命令入口 | A4 |
| `backend/verification/` | 目标版本/资源归属与固定探针的业务验证 | A5 |
| `vscode-extension/` | 新增调查、证据、计划/审批、取消交互，保留原入口 | A6 |
| `infra/` | K3s、RBAC、固定探针、systemd 等经过验证的部署资料 | B 系列 |
| `evals/`、`tests/fixtures/` | 故障/reset/verify、脱敏固定样本、评测与安全回归 | C 系列 |

依赖方向：API -> 登记/领域服务 -> 持久化；编排 -> 诊断适配 -> 只读网关；恢复执行器 -> 已批准动作/策略 -> Kubernetes 写接口；验证器 -> 只读资源/固定探针。配置文件不能让模型绕过上述方向。

多个进程仍可共享同一代码库；不同 Python 模块名不等于 OS/RBAC 权限隔离。初版通过独立用户、配置、凭证和数据库权限实现隔离，实际权限测试必须先于云端试用。

## 配置与秘密边界

详见 [配置约定](../../config/README.md)。A0 提供两份不含秘密的示例，标记 `design_only_not_loaded`，旧 `app.py` 不读取它们。当前有效配置仍只有 `backend/config.py` 中的环境变量。

本地测试使用内存库、假模型配置；未来云端使用独立 PostgreSQL、受限文件目录和进程级凭证引用。诊断进程没有写凭证，执行器的写凭证不放入共享 Agent 配置。云端恢复默认关闭，直到 A3/A4/A5 验收通过。

`.gitignore` 只是误提交防线，不是秘密管理器；已跟踪内容和 Git 历史不会因此被清除。真实凭证不得写入示例、日志、测试夹具或报告，后续还要实现脱敏、权限和秘密扫描。

## A0 验收与下一步

A0 的测试证据、环境差异和当前缺口已写入基线报告；新增配置均是草案，不改现有运行方式。下一项业务任务是 A1 的登记与证据契约，可先用固定样本开发；B0/B1 的资源确认与系统准备独立推进，不以开放旧任务接口替代新架构建设。
